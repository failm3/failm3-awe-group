Для AWE Tool Intelligence стоит начать с **Official MCP Registry и GitHub Search/Releases/Commits**, а npm и PyPI использовать для сопоставления публикаций пакетов. Hugging Face дополняет этот контур моделями и Spaces. Community awesome-каталог полезен для расширения охвата, инженерные статьи — для архитектурного контекста. Найденный Telegram-канал следует оставить кандидатом ручного отбора, а не автоматически подключать.

Это рекомендации о рынке источников, **не измеренная историческая результативность и не разрешение использовать найденные инструменты**. Проверены первичные страницы, документация и отдельные read-only ответы; инструменты не устанавливались и не запускались. Дата наблюдения: 12 ноября 2026 года. Автор: Manus AI. Машиночитаемые записи находятся в соседнем `additional_sources.json`.

## Происхождение и критерии оценки

**A** означает официальный первоисточник. **B** — информационные и исследовательские источники, включая Telegram, сообщества и блоги. **C** — агрегаторы и исторические каталоги, включая Awesome Lists. Это модель владельца AWE, не статистическая оценка точности. Доверие к официальной платформе относится к происхождению платформенных фактов, но не к безопасности любого размещённого проекта.

Технический балл `documented_monitorability_v1` отражает пять проверяемых возможностей: структурное чтение API/RSS, идентификаторы записей, полные даты, доступ к старым записям и документированный механизм мониторинга новых изменений. Каждая получает 1 при прямом подтверждении, 0 только при прямом подтверждении отсутствия и `null`, если сведений недостаточно. Возможности GitHub-каталога могут наследоваться от документированного GitHub API. Доступ к старым записям не означает полный архив, а permalink не гарантирует вечную доступность.

Каждая возможность весит 20 баллов. Итог равен `20 × сумма пяти значений`, только если известны все пять. При неизвестных итог — `null`; отдельно указан subtotal известных возможностей и их число. Поэтому одинаковые 100 баллов у официального реестра и community-списка означают лишь одинаковую документированную наблюдаемость, **не одинаковое доверие или качество**. Расчёты выполнены программно.

Историческая частота публикаций, точность находок, доля инструментов с записанным live test и исторический quality score во всех записях равны `null`. Для их измерения нужен корпус с фиксированным окном, полнотой сбора, дедупликацией и явными числителями/знаменателями. Пример периодичности опроса, API rate limit и период рассылки не заменяют частоту публикаций.

## Источники для основного контура

### Official MCP Registry — A

Реестр содержит стандартизованные метаданные серверов и связывает namespace с подтверждённым GitHub-аккаунтом или доменом. Сам реестр не выполняет аудит кода: его задача — namespace authentication и размещение метаданных; сканирование делегируется пакетным реестрам и агрегаторам. Trust A нельзя переносить на безопасность сервера. [1]

Предпочтительный сбор — неавторизованный read-only `GET /v0.1/servers` с `cursor` и `limit`, затем `updated_since` в RFC 3339. История доступных версий запрашивается через `/v0.1/servers/{serverName}/versions`. У изменяемого `status` нужно учитывать `deprecated` и `deleted`. Документация рекомендует регулярный, но нечастый сбор и приводит пример раз в час: это рекомендация опроса, не установленная частота появления серверов. [2]

Прочитан один живой ответ с `name`, `version`, `publishedAt`, `updatedAt`, `status` и `nextCursor`; это проверка структуры метаданных, не тест работоспособности опубликованного сервера. [3] Реестр обозначен preview, возможны сбросы данных и breaking changes; гарантий uptime и сохранности нет. Полная выгрузка не выполнялась. [1] [2]

Рекомендация: первый источник метаданных после ручного разрешения домена и адаптера. Технический балл — **100**, подтверждены 5 из 5 возможностей. Автоматическое создание кандидатов допустимо только в карантине; `packages`, `remotes` и команды не исполнять.

### GitHub Search, Releases и Commits — A

Официальный REST Search позволяет находить репозитории и получать их идентификаторы и даты. Один запрос ограничен 1000 результатами, страница — 100. Нужно сохранять `total_count` и `incomplete_results`, не утверждая полноту рынка по результатам поиска. Для анонимного поиска документация указывает 10 запросов в минуту; Code Search требует авторизацию. [4]

Для отобранных репозиториев следует читать пагинируемые Releases и Commits. Опубликованные релизы доступны всем, drafts требуют прав. Releases не включают обычные Git tags без release. Дату публикации следует брать из `published_at`: `created_at` не равен дате публикации. Commits дают SHA, даты и фильтры `since`, `until`, `path`; это также способ наблюдать изменения README. Доступная Git-история не гарантирует восстановления удалённых релизов или переписанных веток. [5] [6]

Полезный начальный указатель — `modelcontextprotocol/servers`, но его README прямо предупреждает: это небольшой набор эталонных реализаций, не полный каталог и не production-ready решения. Для discovery сам README направляет в MCP Registry. [7]

Рекомендация: основной канал обнаружения репозиториев и мониторинга уже отобранных проектов. Технический балл — **100**, 5 из 5 возможностей. Trust A относится к GitHub API и официальным платформенным фактам; подлинность каждого автора и его проекта проверяется отдельно. Stars не основание для одобрения.

### Hugging Face Hub API и Spaces — A

Hub предоставляет открытые endpoints, официальный Python/JS клиент и OpenAPI. `list_models` и `list_spaces` поддерживают фильтры, `search`, `author` и сортировку по созданию/последнему изменению. `list_repo_commits` возвращает историю выбранной ревизии модели, Space или dataset, включая даты коммитов. Это полезно для связи приложения, карточки, модели и исходного репозитория. [8] [9]

Предпочтительный сбор — read-only поиск и списки по теме и выбранным владельцам. Сохранять `repo_id`, SHA, карточку и дату изменения. Для явного анонимного режима официальный клиент допускает `token=False`; gated/private объекты не обходить. `lastModified` означает изменение репозитория, не обязательно новый инструмент. Likes, downloads и trending не являются проверкой качества. [9]

Webhooks позволяют наблюдать выбранные репозитории и владельцев, но не дают обычному пользователю открытую глобальную подписку на весь Hub. Доставка может идти не по порядку; предусмотрены retries и `Webhook-Id` для дедупликации. Документирован лимит 1000 triggers за 24 часа — это лимит сервиса, не частота публикаций. Webhooks не создавались. [10]

Рекомендация: основной дополнительный источник AI-компонентов, не замена MCP Registry. Технический балл — **100**, 5 из 5 возможностей. Spaces и модели автоматически не запускать; Git-история относится к репозиториям, не к buckets, у которых её нет. [10]

### PyPI RSS и Index/JSON API — A

PyPI прямо рекомендует RSS для периодического обнаружения новых пакетов и обновлений. Есть feeds новых проектов, последних обновлений и релизов выбранного проекта. Они описаны как последние записи, не как бессрочный полный архив; глубина и срок хранения здесь неизвестны. [11] [12]

Для backfill отобранных проектов предпочтителен JSON Index API `/simple/{project}/`: он показывает доступные версии/файлы, `upload-time`, hashes и `yanked`. JSON API `/pypi/{project}/json` полезен для описания и project URLs. Ключ `releases` в JSON API deprecated; `downloads` всегда равен −1 и не должен использоваться для оценки популярности. Метаданные загрузки не обязательно совпадают с содержимым файла. [13] [14]

Следует учитывать `ETag` и last-serial, ограничивать нагрузку и не строить новые интеграции через XML-RPC. PyPI сохраняет право блокировать безответственный сбор. [11] Рекомендация: источник фактов о публикации Python-пакетов для сопоставления MCP Registry и GitHub; широкий RSS требует тематического фильтра. Технический балл — **100**, 5 из 5 возможностей. На этапе discovery не использовать `pip install`, `uvx` или сборку пакета.

### npm Registry Search и package metadata — A

Официальный API описывает поиск `/-/v1/search` с `text`, `size` и `from`. Один публичный packument был прочитан и разобран: в нём есть `versions`, `dist-tags`, `time.created`, `time.modified` и временные метки версий. Этот образец подтверждает формат, не надёжность SDK и не полноту рынка. Код и tarballs не загружались для выполнения. [15] [16]

Предпочтительный сбор — тематический поиск, затем прямой GET метаданных выбранного URL-encoded имени пакета. Сохранять snapshots, потому что `dist-tags` и deprecation изменяемы. Search score и поля popularity/quality/maintenance нельзя считать результатами проверки AWE. [15] [16]

Не следует переносить старые схемы replication без проверки: `npm/registry` прямо назван архивной документацией. Объявление миграции в GitHub Community указывает новый путь `/registry/_changes`, отдельное получение packument, отмену `include_docs` и streaming modes. Текущую полноту и контракт replication live не тестировали; этот механизм оставлен кандидатом отдельного адаптера. [17] [18]

Рекомендация: добавить read-only поиск и package metadata как источник публикаций JS/TS. Технический итог — **`null`**, subtotal **80**, подтверждены 4 из 5 возможностей; полноценный инкрементальный механизм не зачислен. Не выполнять `npx`, `npm install` и lifecycle scripts.

## Безопасные ограничения автоматического подключения

Подключение источника, исследование ресурса и разрешение исполнения — разные решения. Все перечисленные источники пока `not_enrolled`: не создавались расписания, webhooks, OAuth-подключения, подписки или persistent jobs. После ручного одобрения домена/handle и read-only адаптера допустимо автоматически записывать только неподтверждённые discovery-кандидаты.

Согласно `CONTRACT.md`, ни HTTP 200, ни статус Registry active, ни badge, ни stars/downloads не повышают ресурс до `verified` или `approved`. Исполнимый registry экспортирует только явно approved ресурсы с записанным live test. В этом исследовании таких результатов нет. Не выполнять найденные install-команды, shell-примеры, package scripts, `trust_remote_code` или remote MCP actions.

Network guard должен проверять DNS/IP и каждый redirect, блокируя private, loopback, link-local и metadata addresses. Ссылка из поста не расширяет allowlist. Ограничиваются размер ответа, MIME, timeout и частота чтения. Fetched README, cards, posts и docs считаются недоверенными данными: извлекается информация, а размещённые инструкции не исполняются.

Для каждого утверждения сохраняются первичный URL, время наблюдения, идентификатор, provenance и hash. Секреты и private URLs не попадают в отчёты. Републикации дедуплицируются по canonical repository URL, name+version и SHA; зеркала не умножают число независимых подтверждений. Удаление, yanked/deprecated, ошибки пагинации и пределы истории фиксируются явно. Telegram preview никогда не объявляется полным архивом.
